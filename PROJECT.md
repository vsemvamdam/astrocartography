# AstroSky — карта проекта (рабочая документация руководителя)

Последнее обновление: 26 ноября 2026. Составлено по результатам аудита 26.11.2026.

## 1. Что это

AstroSky.pro — русскоязычный астрологический сервис. Строит натальную карту, астрокартографию,
соляр, лунар, синастрию, гороскоп ребёнка, хорар, спортивные прогнозы и ~12 инструментов.
Всё считается в браузере, без установки. Регистрация нужна только для сохранения карт.

## 3. Архитектура

Статический SPA без сборщика, без `package.json`, без node_modules в продакшене.

- `index.html` — 2569 строк, 173 KB: разметка + **116 KB инлайн-CSS** (2 блока `<style>`).
- **28 копий `index.html`** (по одной на адрес раздела) по ~163 KB — итого ~4.35 MB дублированного HTML
  и ~3.1 MB дублированного CSS. Генерируются `node tools/build_pages.js` из `js/routes.js`.
- **30 скриптов, все без `defer`/`async`** → рендер блокируется полностью.
- Роутинг: `js/routes.js` (список адресов) + `js/app.js` (навигация). Переходы без перезагрузки.
- Локальный предпросмотр: `node tools/build_pages.js --serve` → http://localhost:8080/
- CI: `.github/workflows/pages.yml` пересобирает копии, если их забыли закоммитить.

## 6. SEO

Сделано хорошо:
- 28 адресов, у каждого свои `<title>`, `description`, `canonical`, `<h1>`.
- `sitemap.xml` со всеми адресами, все отдают 200. Несуществующие — 404 ✓.
- JSON-LD: `WebSite`+`Organization` на главной, `BreadcrumbList`+`WebApplication` на разделах,
  `FAQPage` (11 вопросов) на `/voprosy/`.
- `robots.txt` с указанием sitemap. Верификация Google + Яндекс.

Проблемы:
- Каждая из 28 страниц несёт **весь** 163 KB HTML со всеми скрытыми разделами → дублирование
  контента; Google может считать страницы почти идентичными.
- `og:image` — только на главной, у разделов нет.
- Нет `hreflang` (продукт двуязычный по замыслу — русского и английского поиска нет).

## 7. Безопасность (аудит 26.11.2026)

Хорошо:
- Секретов и токенов в репозитории и в истории нет (проверено по `ghp_`, `gho_`, `client_secret`,
  формату токена бота).
- `.git/`, `tools/`, `FIREBASE.md`, `firestore.rules`, `.github/` наружу не отдаются (404) ✓
- `firestore.rules`: каждый читает и пишет только своё поддерево `users/{uid}/**` ✓
- Экранирование `esc()` есть во всех файлах, где используется `innerHTML` (80 мест, 0 неэкранированных
  конкатенаций). Ключи Firebase публичны по замыслу и защищены правилами.

Проблемы:
- **Ни одного security-заголовка**: нет HSTS, CSP, X-Content-Type-Options, X-Frame-Options,
  Referrer-Policy, Permissions-Policy.
- **`/CLAUDE.md` отдаётся публично (200)** — внутренняя документация видна всем.
- Нет CAA-записи (любой CA может выпустить сертификат на домен).
- DMARC `p=none` — письма с подделкой домена не блокируются.
- HTTP/1.1, хотя сервер поддерживает HTTP/3 (заголовок `Alt-Svc` есть).
- 2 изображения без `alt` (декоративные облака — с `alt=""`, это нормально).

- Расписание GitHub Actions ненадёжно — README сам это признаёт и дублирует запуск через
  cron-job.org; требует ручного обновления токена.
- Локальная копия имеет `core.autocrlf=true` без `.gitattributes` → 65 файлов в рабочем дереве
  с CRLF, 30 с LF. Не ломает сайт (Caddy отдаёт как есть), но создаёт шум в диффах.
- Нет `package.json`, нет линтера, нет unit-тестов (только три ручных проверочных скрипта).

## 10. Правила проекта (обязательны для агентов)

1. **Вендоринг чужих библиотек.** Текст лицензии берётся ТОЛЬКО из шапки самого файла, из
   `package.json` или из `LICENSE` официального пакета. Никогда по памяти и никогда не
   додумывается. Если автора установить не удалось — остановиться и спросить, а не подставлять
   правдоподобное имя. (26.11.2026: агент вписал в лицензию astronomy-engine вымышленного автора
   «Bill Conley»; настоящий — Don Cross. Ошибку исправил руководитель.)
   Рядом с вендоренным файлом обязательны: версия, ссылка на источник и sha256 файла.
   Имя файла лицензии — по образцу уже принятых: `JSPDF-LICENSE`, `LEAFLET-LICENSE`, `ASTRONOMY-LICENSE`.
2. **Никогда не выдавать спортивные прогнозы за гарантию исхода и не позиционировать их как
   способ заработка.** Не добавлять призывы к ставкам и партнёрские ссылки на букмекеров.
3. **Не менять версию astronomy-engine** без пересборки таблиц Хирона и астероидов
   (`tools/build_tables.js`) — они посчитаны именно на 2.1.19.
4. **Правки в отдельной ветке**, публикация в `main` — только после согласования с владельцем.
5. **После любой правки `index.html` или `js/routes.js`** — `node tools/build_pages.js`,
   иначе 28 копий разойдутся с оригиналом. **И закоммитить то, что он переписал, вместе с
   самой правкой.** Проверка: после сборки `git status --short` чист, а `--check` говорит
   «up to date». (26.11.2026: правку `index.html` закоммитили, а 27 пересобранных копий —
   нет; репозиторий на время разошёлся. Ошибку нашёл и исправил руководитель.)
6. **Расчёты не ломать.** Любая правка ядра проверяется `tools/test-core.js`,
   `tools/natal-check.js`, `tools/sotis-check.js`: макс 13″ против Сотис, 13/13 домов против ZEUS.
7. **Никогда не переписывать `document.body` (и `innerHTML` контейнера целиком).**
   `document.body.innerHTML = '…'` выбрасывает всю страницу: навигацию, подвал, все разделы,
   SEO-текст. Предупреждения и заглушки добавляются ВСТАВКОЙ нового элемента
   (`insertBefore` / `appendChild`), а не заменой содержимого.
   (26.11.2026: fallback при незагруженном движке затирал `body` — при сбое сайт терял
   25 ссылок, 36 секций, логотип и подвал, оставалось 102 символа текста вместо 3100.
   Ошибку нашёл и исправил руководитель.)
8. **Работу коммитить, а не оставлять в рабочем дереве.** «Ветка готова к слиянию» без
   коммитов — это потерянная работа. Проверка: `git log main..<ветка>` не пуст.
9. **Тексты интерфейса — сразу на русском и английском** (когда появится английская версия,
   иначе придётся переделывать). Технические комментарии в коде — на английском.
10. **Рабочее дерево задаётся в карточке задачи.** Задачи, меняющие файлы проекта, создаются
   только с `--project astrosky --workspace worktree` — тогда у исполнителя своё дерево и своя
   ветка. Если дерево пустое — **не работать в чужом**, а сообщить о блокировке.
   (26.11.2026: три задачи для `developer-s` упали в `blocked` из-за `scratch`-workspace без
   репозитория — это была моя ошибка в постановке; а задача `t_780fd2dc` была сделана прямо
   в главном дереве, в чужой ветке, рядом с работой другого агента. Обе ситуации разобраны.)
11. **Меняешь `js/*.js` — обнови версию в `index.html`.** Теги подключаются как
   `файл.js?v=СТАМП`. Без обновления версии браузеры отдают старый файл из кеша
   (`Cache-Control: max-age=600`, 10 минут): правка «сделана, но не видна».
   (26.11.2026: правка `js/sport-view.js` была бы незаметна, если бы версию не подняли.)
12. **Незакоммиченное в общем дереве может быть перезаписано параллельным агентом.**
   Перед отчётом о готовности: `git status` чист по твоим файлам. (Дополняет правило 8:
   там про потерю ветки, здесь — про конфликт с соседом по дереву.)
13. **Ставить `defer` — проверять, что ничто не читает чужие глобали во время парсинга.**
   Скрипт с `defer` выполняется ПОСЛЕ разбора HTML. Любая инлайн-проверка вида
   `if (typeof Something === 'undefined')` вне `DOMContentLoaded` сработает **всегда**:
   отложенный скрипт к этому моменту ещё не выполнен. Проверки состояния — только внутри
   `DOMContentLoaded` (или на `load`). Правило действует и при слиянии: правка порядка
   загрузки в одной ветке ломает проверку из другой.
   (26.11.2026: ветка производительности добавила `defer` движку, и предупреждение
   «движок не загрузился» начало показываться на полностью рабочем сайте —
   `window.Astronomy` был `object`, а полоса с ошибкой висела. Нашёл и исправил руководитель
   в обеих ветках, чтобы порядок слияния был не важен.)
14. **Формат картинок проверять по потребителю, а не по удобству.** `og:image` для соцсетей —
   **только PNG или JPEG**: ни один крупный сервис (Facebook, X, Telegram, VK, LinkedIn)
   не отображает SVG, превью останется пустым. SVG годится для иконок и логотипов в самой
   странице, но не для превью в чужих лентах.
   (26.11.2026: пять картинок превью сделаны в SVG 1200×630 — дизайн верный, формат нет.)
15. **Начало `index.html` — ровно `<!doctype html>` и LF.** `tools/build_pages.js` отказывается
   работать, если после доктайпа стоит CRLF, а `core.autocrlf=true` без `.gitattributes`
   норовит его туда поставить. Симптом: «must start with "<!doctype html>" and a new line»
   и ни одна копия не собирается.
16. **Исполнителя выбирать по доступной мощности, а не по названию роли.** Профиль `operator`
   работает на локальной модели (llamacpp, 127.0.0.1:18434) с реальным окном контекста меньше,
   чем предполагает Hermes: длинные задачи падают с `rc=75` (квота) или «does not fit context
   window», после чего dispatcher держит задачу в cooldown и **сам не перезапускает**.
   Для задач с большим объёмом текста использовать `devxero` / `developer-s` (внешние провайдеры).
   (26.11.2026: три задачи у operator упали подряд — по контексту и по квоте; карточку пришлось
   пересоздавать на devxero.)
17. **Заметил приёмку — не молчи.** Если исполнитель отчитывается «готово», а проверка показывает
   незакоммиченные файлы, ложное срабатывание или невыполненный критерий — принимать нельзя.
   Проверять самому: `git log main..<ветка>`, `git status`, прогон в браузере.
   (26.11.2026: трижды пришлось коммитить чужую работу и один раз исправлять регрессию.)
18. **Создавая задачу с worktree, проверь, какой HEAD у главного дерева.** `git worktree`
   ветвится не от `main`, а от **текущего** HEAD репозитория. Если главное дерево стоит на
   рабочей ветке, новая задача получит чужую работу в своей истории — а при слиянии она
   уедет вместе с ней. Перед созданием задачи: `git checkout main` в главном дереве.
   Проверка после создания: `git log --oneline main..<ветка задачи>` должен быть **пуст**
   (работа исполнителя ещё не начиналась).
   (26.11.2026: четыре задачи получили в свою ветку коммиты вендоринга движка только потому,
   что главное дерево стояло на рабочей ветке. Исправлять базу у уже запущенной задачи нельзя —
   воркер работает в этом дереве; такие ветки править перед слиянием, а не во время работы.)
19. **Монитор, написанный в ветке, проверяет ПРОДАКШЕН — не путать окружения.**
   Скрипт доступности писался в worktree, где вендоринг движка уже сделан, а проверял живой сайт,
   куда вендоринг не выложен. Итог: `/js/vendor/astronomy.browser.min.js` → 404, накопилось
   `failures: 3`, и при настроенном токене владелец получил бы ложное «сайт недоступен» на
   полностью работающем сайте (спасло лишь то, что токен не задан).
   Правило: проверка не должна хардкодить имена файлов своего окружения — путь брать из самой
   страницы и проверять то, что реально отдаётся. И разделять «сайт упал» от «моя проверка
   рассинхронизирована»: второе не накручивает счётчик сбоев и не поднимает тревогу.
   (26.11.2026, задача t_df42c601.)
20. **Всегда добавлять `.gitattributes` с `eol=lf`.** `core.autocrlf=true` без этого файла переводит
   LF в CRLF при checkout, и дисковая копия вендоренных файлов не совпадает с committed-версией
   (sha256 меняется). Это косметически для JS, но портит контроль целостности. (26.11.2026: после
   слияния вендоринга движка дисковая копия имела CRLF, committed — LF. Добавлен `.gitattributes`.)
21. **Задачу нельзя закрыть по текстовому отчёту.** Основание для `done` — только артефакт,
   проверяемый командой: непустой `git log main..<ветка>`, чистый `git status`,
   прошедшие `build_pages.js --check` и `test-core.js`, приложенный вывод прогона.
   Отчёт без diff и без команды-доказательства = задача не сделана.
   (26.11.2026: три задачи подряд были закрыты текстом «реализовано», тогда как артефактов
   в репозитории не было вообще — работа сделана руководителем до исполнителя.)
22. **Коммитить по ходу, а не в конце.** Каждый законченный шаг — отдельный коммит с внятным
   сообщением. Незакоммиченная работа в worktree теряется при его очистке, и восстановить
   её можно только из reflog, пока жив объект. (Дополняет правило 8.)
23. **Перед `rebase` — резервная точка.** `git tag -f backup/<ветка>-pre-rebase HEAD`.
   При `git rebase` конфликт решается **`--ours` = UPSTREAM (`main`)**, `--theirs` = свой коммит —
   интуиция здесь обратная, и выбор наугад уничтожает работу.
   **После `rebase` сверять контрольные цифры, а не доверять статусу git:** `Successfully rebased`
   печатается и тогда, когда изменения потеряны. Снимать ДО и сравнивать ПОСЛЕ: размер ключевого
   файла, число `defer`, имя версионированного ресурса, число собранных страниц.
   (26.11.2026: `rebase` ветки производительности с `--ours` вернул `index.html` к 174 KB,
   выбросив вынесенный CSS и 55 300 строк правок; git при этом сообщил об успехе. Поймано
   сверкой размеров, восстановлено из reflog.)
24. **После каждого слияния в `main` — прогон тестов и независимое ревью, на десктопе и на мобильном.**
   Минимум: `node tools/build_pages.js --check`, `node tools/test-core.js`,
   `node tools/natal-check.js`, `node tools/sotis-check.js` (эталон 13″ и 13/13 домов),
   плюс ручная проверка живого сайта в двух разрешениях. Регрессия, найденная в `main`, —
   остановка и откат, а не «починим следующим коммитом».
25. **Тихий отказ запрещён.** Успешный код возврата не должен скрывать ошибку. Проверка обязана
   различать «объект сломан» и «моя проверка рассинхронизирована», писать в журнал причину,
   а не только итог, и уведомлять о сбое. Сценарии отказа тестируются наравне с успешными:
   скрипт, у которого проверен только зелёный путь, не проверен.
   (26.11.2026: монитор доступности на ASCII-stdout молча терял текст тревоги, а `gh` под «голым»
   окружением планировщика без `git` в `PATH` молча не отправлял запуск — два случая одного класса.)
