## 3. Найденные проблемы

Отсортированы по риску. **Ни одна не исправлялась** — все оформлены задачами.

### P0. astronomy-engine грузится только с jsDelivr

Ядро всех расчётов подключается одной строкой с внешнего CDN. Локально его **нет**
(в `js/vendor/` только jspdf, leaflet, telegram). Нет SRI, нет fallback, нет второго источника.

**Проверено в браузере:** при блокировке `cdn.jsdelivr.net` страница навсегда остаётся
`readyState=loading`, `window.ACG`/`Astronomy`/`NATAL` = `undefined`, не строится ни одна карта —
пользователь видит мёртвую страницу без объяснений.

Сам CDN здоров (отдаёт файл за 0.2 с, код 200) — это не текущий сбой, а непокрытый риск:
**один сторонний сервис держит весь продукт.** Для российской аудитории, где jsDelivr
периодически недоступен, это реальный сценарий.

### P1. Нет ни одного security-заголовка

`curl -D -` показывает только `Server: Caddy`. Нет HSTS, CSP, X-Content-Type-Options,
X-Frame-Options, Referrer-Policy, Permissions-Policy. HTTP/1.1, хотя HTTP/3 объявлен.

### P1. `/CLAUDE.md` отдаётся публично

Внутренняя документация проекта (как генерируются страницы, куда кладутся секреты)
доступна любому по адресу `astrosky.pro/CLAUDE.md` — 200 OK.

### P1. Внешний триггер обновления данных мёртв

Копия ESPN обновляется раз в полчаса **только если работает внешний запуск** — README сам
предупреждает, что расписание GitHub ненадёжно.

Замерено: возраст копии **347 минут (5.8 часа)**. За сутки workflow запускался **2 раза
вместо 48**. Из 81 запуска за всю историю лишь **5** были внешними — механизм почти не работает.

Хорошая новость: сам код обрабатывает устаревание **правильно** — через 2 часа показывает
предупреждение «Свежее получить не удалось: счёт и составы могут отставать» и честно пишет
время данных. Проблема только в триггере.

### P1. Дисклеймер спортивных прогнозов существует, но спрятан

Вкладка «Спорт» публикует коэффициенты букмекеров и прогнозы по Фроули. **Дисклеймер есть**
(`js/sport-view.js:173`, живёт с 23.11.2026): «Это прогноз для интереса, не гарантия результата;
не используйте его как основание для ставок».

**Моя ошибка в первой версии отчёта:** я написал «дисклеймера нет», искав только в
`js/page-texts.js` (тексты разделов) и не проверив рендереры. Дисклеймер лежит в интерфейсе
карточки матча. Ошибку нашёл агент при подготовке предложения и опроверг мой вывод с
проверкой по коду и живой странице. Исправлено.

Настоящая проблема — **где** он находится (замерено):
- в списке матчей (первый экран вкладки) — **не виден**;
- в статическом HTML `/sport/` — **отсутствует** (в JS-рендере, краулер без JS его не увидит);
- в карточке матча — есть, но в конце абзаца на 1639 знаков (последние ~10 % текста,
  шрифт 12.5 px, цвет `--muted`).

То есть человек листает список, видит чипы «Арсенал · явно», «Реал · умеренно» — оценку
уверенности — и не встречает предупреждения. Риск не исчез, он сместился: предупреждение
есть, но не работает там, где нужно.

При этом проект **сам** провёл честный аудит метода и открыто публикует результат:
карта назвала победителя — он выиграл в 36% при 36% по ставкам (+0.1 ± 0.9);
при «явном перевесе» 34% против 34%. По пяти видам спорта — то же: метод не добавляет
к коэффициентам ничего. Ставка на фаворита угадывает на 10–20 пунктов больше.

Это редкая интеллектуальная честность, и её надо не спрятать, а сделать явной — тогда она
станет отличием от конкурентов, обещающих точность.

### P1. Мобильный интерфейс и доступность

Проверено на локальном стенде в реальном рендере (390×844) и на живом сайте:

- Контраст `--faint #5E6D86` на фоне панели — **3.55:1** при норме WCAG AA 4.5:1.
  Используется для мелкого текста: координаты, подсказки, подписи (11–12.5 px).
- **19 целей касания меньше 32 px**; кнопки cookie-плашки `min-height: 38px` при норме 44.
- Вкладки меню на телефоне: мало вертикального места и почти нет зазора между «Натал»
  и «Инструменты» — легко промахнуться. Активная вкладка на мобильном не выделяется.
- **Cookie-плашка перекрывает колесо гороскопа** и подпись «Небо сейчас» — то есть первый
  экран продукта не виден, пока не нажмёшь кнопку.

Хорошее: горизонтального переполнения нет, шрифты 16–17 px с хорошим интерлиньяжем,
основные кнопки 52–56 px, `alt=""` у декоративных облаков — правильно.

### P2. Производительность

Замерено: TTFB ~1.55 с, HTML 173 KB (29.8 KB gzip). Крупнейшие передачи:

| Файл | raw | gzip |
|---|---|---|
| `js/data.js` | 983 KB | 561 KB |
| `js/asteroids-extra-data.js` | 529 KB | **529 KB (не сжимается)** |
| `js/interpret.js` | 175 KB | 50 KB |
| `js/natal-view.js` | 98 KB | 33 KB |

30 блокирующих скриптов; таблицы астероидов, Хирона и знаменитостей грузятся всегда, хотя
README утверждает, что они грузятся по запросу; 116 KB CSS продублированы в 28 файлах
(3.1 MB лишнего).

### P3. SEO — база хорошая, есть что достроить

Сделано хорошо: 28 адресов со своими `title`/`description`/`canonical`/`h1`, полный sitemap
(все адреса отдают 200, несуществующие — 404), корректный JSON-LD (WebSite, Organization,
BreadcrumbList, WebApplication, FAQPage с 11 вопросами), robots.txt, верификация Google и
Яндекса, а Метрика грузится **только после согласия на cookies** — это правильно.

Проблемы: каждая из 28 страниц несёт **полный** 163 KB HTML со всеми чужими разделами
(риск дубликата для поисковика); нет `hreflang`; `og:image` одинаковый везде;
нет своей страницы 404; **нет блога** — а это самая большая неиспользованная возможность,
весь трафик идёт только с инструментов.

### Прочее

- Ветки-мусор: `tmp-probe`, `ios-ci`, `qa` (отстала на 46 коммитов), `ios-app`.
- CARTO отключён: `CARTO_KEY = ''` — тёмная подложка карты города не работает.
- `document.write` в `index.html` (3 места) — устаревший API.
- DMARC `p=none`, CAA-записи нет.
- Нет `package.json`, линтера и unit-тестов — только три ручных проверочных скрипта.
- Локальная копия: `core.autocrlf=true` без `.gitattributes` → 65 файлов CRLF, 30 LF.

### Что проверено и чисто

- Секретов, токенов и ключей в репозитории и **в истории** — нет.
- `.git/`, `tools/`, `FIREBASE.md`, `firestore.rules`, `.github/` наружу не отдаются (404).
- `firestore.rules` корректны: каждый читает и пишет только своё поддерево.
- XSS: экранирование `esc()` есть во всех 8 файлах с `innerHTML` (80 мест),
  неэкранированных вставок — 0.
- Ключи Firebase публичны по замыслу и защищены правилами.
- HTTP→HTTPS 308, www→apex 301.

## 6. Вывод

**Проект сильнее, чем выглядит снаружи.** Расчётное ядро работает на уровне лучших
профессиональных программ и подтверждено внешними эталонами — это редкость. Функциональность
широкая, честность в спортивной статистике — редкое качество.

Слабые места — не в астрономии, а в инженерии и эксплуатации: единственная точка отказа
на CDN, отсутствие security-заголовков, мёртвый триггер данных, дублирование HTML
и неиспользованный контентный канал для привлечения аудитории.

**Продакшен не тронут.** Все находки оформлены задачами, каждая правка — в отдельной ветке
и на согласование. Следующий шаг: отчёт по конкурентам и модели монетизации (этапы 3–4).
